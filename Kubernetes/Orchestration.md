# Orchestration
**오케스트레이션(Orchestration)이란?** 여러 시스템, 프로세스, 서비스를 효율적으로 조정하고 관리하는 작업을 의미한다. 

마치 오케스트라의 지휘자가 다양한 악기들이 조화를 이루게끔 지휘하는 것처럼 **여러 컴퓨터 시스템이나 애플리케이션을 조정하여 원활하게 협력하도록 만드는 것**이다.

컨테이너 하나 정도는 docker run으로 직접 관리할 수 있지만 수십~수천 개의 컨테이너를 여러 서버에 걸쳐 운영하려면 사람이 일일이 관리하기가 불가능해진다. 그래서 이걸 **자동으로 처리해주는 도구**가 바로 Orchestration 도구이다.

# Orchestration이 하는 일
**자동 배포** : 여러 서버에 컨테이너를 자동으로 분산해서 배치한다.   

**자동 확장(Scaling)** : 트래픽이 몰리면 컨테이너 개수를 자동으로 늘리고 트래픽이 줄면 다시 줄인다.     

**자동 복구(Self-healing)** : Health check에서 문제가 감지된 컨테이너를 자동으로 종료하고 새 컨테이너로 교체한다.       

**로드 밸런싱** : 여러 컨테이너에 트래픽을 고르게 분산시킨다.   

**롤링 업데이트** : 서비스 중단 없이 컨테이너를 하나씩 순차적으로 새 버전으로 교체한다. 

# Orchestration이 필요한 이유
**관리 복잡도 해결** : 컨테이너 개수가 많아지면 어떤 서버에 뭐가 떠 있는지 사람이 직접 파악하고 관리하기 불가능해지기 때문이다.

**트래픽 대응(자동 확장)** : 트래픽이 몰리거나 줄어들 때마다 컨테이너 개수를 실시간으로 조절해야 하는데 사람이 수동으로 대응하기 어렵기 때문이다.

**장애 자동 복구** : 컨테이너나 서버에 장애가 생겼을 때, 사람이 알아채기 전에 자동으로 감지하고 복구해서 서비스 중단을 최소화해야 하기 때문이다.

# Orchestration의 대표적인 도구
**Kubernetes(k8s)** : 가장 널리 쓰이는 오케스트레이션 표준이고 대규모 운영에 강하다.

**Docker Swarm** : Docker에 내장된 오케스트레이션 도구이고 상대적으로 간단하다.

**Amazon ECS** : AWS의 관리형 컨테이너 오케스트레이션 서비스이다.

# Docker와의 관계
**Docker**는 컨테이너를 만들고 실행하는 도구이고, **오케스트레이션 도구**는 그 컨테이너들을 대규모로 관리하는 도구이다. 

비유하자면, Docker가 붕어빵 하나를 굽는 방법이라면 오케스트레이션은 붕어빵 공장 전체를 자동으로 운영하는 시스템이라고 볼 수 있다. 실무에서는 Docker로 이미지를 만들고 Kubernetes 같은 오케스트레이션 도구로 **그 이미지를 대규모로 배포 및 운영하는 흐름이 일반적**이다.

# Orchestration의 구성 요소
(Kubernetes 기준)

## Pod  
Kubernetes에서 배포되는 가장 작은 단위  
(하나 이상의 컨테이너를 묶어서 하나의 그룹으로 관리하는 단위)       
보통 컨테이너 하나당 Pod 하나로 구성되는 경우가 많다.   
같은 Pod 안의 컨테이너들은 네트워크와 저장공간을 공유한다.

## Node          
Pod가 실제로 배치되어 실행되는 물리적/가상 서버 한 대를 의미한다.   
여러 개의 Node가 모여서 하나의 클러스터를 이룬다.

## Cluster     
여러 개의 Node를 하나로 묶어놓은 전체 집합을 의미한다.      
Orchestration 도구는 이 클러스터 전체를 하나의 단위처럼 다루면서 Pod들을 적절히 분산 배치한다.

## Deployment    
"이 애플리케이션을 몇 개의 Pod로, 어떤 이미지로 실행할지"를 선언적으로 정의하는 설정이다.       
예를 들어 "이 앱은 항상 Pod 3개가 떠 있어야 한다"고 Deployment에 정의해두면, 하나가 죽어도 Kubernetes가 자동으로 감지해서 다시 3개를 맞춰준다.      
앞서 다룬 자동 복구(Self-healing)가 실제로 동작하는 원리가 바로 이 Deployment 개념이다.

## Service     
여러 개의 Pod에 접근할 수 있는 하나의 고정된 진입점(네트워크 주소)을 제공한다.      
Pod는 죽었다 다시 생기면 IP가 바뀔 수 있는데, Service는 이 변화와 상관없이 항상 같은 이름/주소로 접근할 수 있게 해준다.     

## ConfigMap / Secret   
애플리케이션 설정값이나 민감한 정보(비밀번호, API 키 등)를 컨테이너 코드와 분리해서 관리하는 오브젝트다.    
ConfigMap은 일반 설정값을, Secret은 민감한 정보를 저장하는 용도로 구분해서 쓴다.
