# GitOps
**GitOps란?** 애플리케이션 코드부터 시작해서 인프라, 네트워킹, CI/CD 파이프라인 등 **전체적인 애플리케이션 생태계에 대한 구성들을 모두 Git에 저장하여 관리하는 방식**이다. 쿠버네티스는 yaml 파일으로 작성되는 매니페스트 파일로 자동 배포와 인프라 환경을 구축한다.

# GitOps의 핵심 원칙
GitOps의 핵심 원칙은 쿠버네티스의 특징인 **선언형 방식**과 Git의 주요 기능인 **버전관리**와 **PR**을 결합하여 클라우드 네이티브 환경을 안전하고 효율적으로 관리한다.

## 선언형 방식
모든 구성들이 일련의 명령어들로 관리되는 것이 아닌 **일련의 사실으로 구성해 이러한 사실들이 실제 환경에서 보장된다는 의미**이다. 쿠버네티스에서는 구성이 매니페스트 파일으로 선언할 수 있는데 매니페스트 파일을 Git으로 저장하여 관리한다고 보면 된다. 매니페스트 파일이 저장된 Git을 쿠버네티스의 단일 진실 공급원(SSOT)으로 사용할 수 있다.

**SSOT(Single source of truth)이란?** 모든 데이터 요소들을 한 곳에서만 관리하도록 하는 관례이다. 즉, 쿠버네티스에서 SSOT는 클러스터의 상태는 오직 Git에 저장된 매니페스트 파일로만 보장한다.

## 버전관리와 불변성
Git과 같은 버전관리 시스템에서 구성파일이 저장되기 때문에 **롤백이 단순**하다. 명령어를 사용하여 클러스터가 언제든지 이전 상태로 되돌릴 수 있다. 그리고 **저장이 된다면 특정 버전은 불변성을 가진다는 의미**기도 한다.

## 변경사항 승인과 자동 반영
**Git에 구성파일이 모두 반영되면 모든 변경사항이 쿠버네티스에 자동으로 적용**되도록 하는 것이다. 여기서 중요한 점은 **쿠버네티스 권한이 없어도 Git 레포지토리 접근만 가능하면 클러스터의 상태를 변경**할 수 있다. 하지만 곧바로 Git에 반영하면 위험할 수도 있다.

그래서 Git에서는 **PR(Pull Request)** 기능을 제공하기 때문에 이 기능을 사용하여 변경사항을 상호검토해 Human error에 대한 위험을 줄일 수 있다.

## 지속적 조정 및 알림
시스템의 상태를 선언하고 버전 관리를 하면 소프트웨어 에이전트는 **실제 상태가 원하는 상태와 다를 때마다 사용자에게 알려줄 수 있다.** 에이전트를 사용하면 **전체 시스템이 자동 복구**를 할 수 있다. 그리고 단순히 노드나 파드 장애를 넘어 human error를 수정하는 것까지 포함한다. 이러한 상황에서 소프트웨어 에이전트가 운영에 대한 피드백과 제어 루프 역할을 한다.

# GitOps의 비판적 시점
## pull 유연성 낮음
대부분의 pull 방식 GitOps 에이전트는 쿠버네티스 안에서만 동작하며 쿠버네티스가 아닌 다른 환경에 배포하려면 결국 그 환경으로 설정을 push해야 한다. **VM, 베어메탈, 레거시 시스템이 섞인 인프라라면 pull 모델을 억지로 끼워 맞추기보다 push 방식을 사용하는 게 더 실용적**이다.

## 시크릿 관리 복잡도 높음
push 기반 배포 전략은 자동화의 특정 측면을 단순화하지만 경직성과 잠재적 보안 문제로 이어질 수 있는 반면, pull 기반 배포는 시크릿과 설정 관리의 복잡성이 추가되는 대가로 내부관리와 보안을 강화한다. **Git에 평문 시크릿을 넣을 수 없으니 별도 레이어가 반드시 필요하다.**

## 드리프트 감지의 엣지케이스
CLI를 통한 **out-of-band 변경은 self-heal 옵션을 켜야만 감지·복구**되는데, 이 옵션은 기본값이 꺼져 있어 **별도 설정 없이는 애초에 잡히지 않는다**. 옵션을 켜더라도 폴링 주기 특성상 최대 180초 가까이는 드리프트가 그대로 방치될 수 있고, 반대로 너무 적극적으로 되돌리면 HPA 같은 다른 컨트롤러가 관리하는 필드까지 강제로 되돌려버려 서로 충돌하는 역설도 생긴다.

# Push 방식 CI/CD와의 차이점
**CI/CD 방식** : 클러스터 바깥에 있는 CI 서버가 클러스터 안으로 연결을 열어 `kubectl apply` , `helm upgrade` 를 실행한다. CI 서버가 클러스터의 kubeconfig이나 서비스 어카운트 토큰을 RW(읽기 + 쓰기) 권한을 들고 있어야 한다.

**GitOps 방식** : 클러스터 안에 있는 오퍼레이터가 클러스터 바깥의 Git으로 연결을 열어 지속적으로 폴링, Git 저장소는 애초에 인증정보를 요구하지 않고 클러스터 인증정보는 클러스터 밖으로 한 발짝도 나가지 않는다.

## CI/CD와 GitOps 비교표
| **항목** | **CI/CD** | **GitOps** |
| --- | --- | --- |
| 연결 시작 주체 | CI 서버(클러스터 밖 → 안) | 오퍼레이터(클러스터 안 → 밖) |
| 클러스터 인증정보 위치 | CI 서버에 저장(외부 노출) | 클러스터 내부에 고정 |
| 방화벽 요구사항 | inbound 포트 개방 필요 | outbound만 있으면 됨 |
| 드리프트 감지 | 안 됨(배포 시점에만 적용) | 지속적 재조정으로 자동 감지 및 복구 |
| 실행 도구 | Jenkins, GitHub Actions, CircleCI | ArgoCD, FluxCD |
| 유연성 | K8s 아닌 환경에도 동일하게 적용 쉬움 | 사실상 쿠버네티스 환경에 특화 |
