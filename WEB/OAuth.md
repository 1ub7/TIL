# OAuth
**OAuth(Open Authorization)란?** 인터넷 사용자들이 비밀번호를 제공하지 않고 다른 웹 사이트 상의 자신들의 정보에 대해 웹 사이트나 애플리케이션의 접근 권한을 부여할 수 있는 공통적인 수단으로서 사용되는 **접근 위임을 위한 개방형 표준 프로토콜**이다.    
즉, 애플리케이션을 이용할 때 사용자가 해당 어플리케이션에 ID,PW등의 정보를 제공하지 않고 사용자는 이용 중인 애플리케이션(Client)이 아니라, 해당 인증 서버가 인증 과정을 처리해주는 방식이다.    
(인증 프로토콜이 아니라 인가 프레임워크)

# OAuth의 탄생 배경
OAuth 이전엔 사용자가 제3자 앱에 자기 비밀번호를 직접 넘기는 비밀번호 안티패턴이 표준이었다. 그치만 구현 복잡성이 커지면서 OAuth로 단순화 및 재설계를 한 것이다.

# OAuth의 역할
요약하자면 OAuth는 **비밀번호를 넘기지 않고** 범위가 제한되고 언제든 철회 가능한 접근 권한을 제 3자에게 위임하는 것이다.

**Resource Owner** : 리소스 소유자이고 본인의 정보에 접근할 수 있는 자격을 승인하는 주체이다. **클라이언트를 인가(Authorize)하는 역할**을 수행하고, 인증이 완료되면 동의를 통해 권한 획득 자격(Authorization Grant)을 클라이언트에게 부여한다.

**Client** : Resource Owner의 리소스를 사용하고자 **접근 요청**을 하는 어플리케이션이다.

**Resource Server** : Resource Owner의 정보가 저장되어 있는 서버이다.

**Authorization Server** : 권한 서버이다. 인증/인가를 수행하는 서버로 **클라이언트의 접근 자격을 확인**하고 **Access Token을 발급**하여 권한을 부여하는 역할을 수행한다.

# OAuth 주요 용어
**Authentication(인증)** : 이 사람이 누구인지 신원을 확인하는 단계이다.

**Authorization(인가)** : 자원에 접근할 권한을 부여하고 리소스 접근 권한이 담긴 Access Token을 제공한다.

**Access Token** : 리소스 서버에게서 리소스 소유자의 정보를 획득할 때 사용되는 만료 기간이 있는 Token이다.

**Refresh Token** : Access Token 만료시 이를 재발급 받기위한 용도로 사용하는 Token이다.

**Scope** : 클라이언트가 요청하는 접근 권한의 범위를 명시하는 파라미터이다. 필요한 최소한의 권한만 요청하는 게 원칙이다. 인증 서버는 사용자에게 동의 화면에서 Scope 목록을 사람이 읽을 수 있는 문장으로 보여준다. 

**Redirect URI** : 인증 완료 후 인증 코드를 돌려받을 목적지 주소이다. 인증 서버에 앱을 등록할 때 사전에 정확히 등록해둬야한다. 

**Client ID/Secret** : 인증 서버에 애플리케이션을 등록할 때 발급받는 신원 정보이다.

구분 | Client ID | Client Secret  
|---|---| --- |
성격 | 공개 정보(Public) | 비밀 정보(must stay secret)
역할|"어떤 앱이 요청하는지" 식별 | "이 앱이 진짜 그 앱이 맞는지" 증명
노출 여부 | URL에 노출돼도 무방 | 절대 클라이언트 코드/URL에 노출 금지

# 권한 부여 방식
**Authorization Code Grant | 권한 부여 승인 코드 방식**     
권한 부여 승인을 위해 자체 생성한 Authorization Code를 전달하는 방식으로 많이 쓰이고 기본이 되는 방식이다. 간편 로그인 기능에서 사용되는 방식으로 **클라이언트가 사용자를 대신해 특정 자원에 접근을 요청**할 때 사용되고, Refresh Token의 사용이 가능하다.

설계 자체가 토큰이 브라우저를 절대 거치지 않도록 만들어졌기 때문에 기본이 되는 방식이다. 사용자가 로그인하고 동의하면 인증 서버는 Access Token을 바로 주지 않고 임시 코드만 브라우저를 통해 Client에게 돌려주는 방식이다.

**Implicit Grant | 암묵적 승인 방식**       
자격증명을 안전하게 저장하기 힘든 클라이언트(ex:JavaScript등의 스크립트 사용 브라우저)에게 최적화된 방식이다. 암시적 승인 방식에서는 **권한 부여 승인 코드 없이 바로 Access Token이 발급**된다. 

자체 백엔드 서버가 없거나 있어도 client_secret을 안전하게 보관할 서버 사이드 저장소가 마땅치 않았다. 그치만 이걸 JS 코드 안에 넣으면 누구나 열어볼 수 있으니 의미가 없어지는 문제가 있었다. 그래서 로그인 끝나자마자 바로 Access Token을 브라우저로 던져주는 방식으로 단순화한 것이다.

**Resource Owner Password Credentials Grant | 자원 소유자 자격증명 승인 방식**      
간단하게 username, password로 Access Token을 받는 방식이다. Refresh Token의 사용도 가능하다. 사용자의 실제ID와 비밀번호를 Client가 직접 입력받아서 인증 서버에 그대로 전달하는 구조인데, 이 방식은 OAuth의 정의와 모순되는 부분이기에 Client와 인증 서버가 같은 회사이고 완전히 신뢰할 수 있는 경우에만 사용하는 방식이다.

**Client Credentials Grant | 클라이언트 자격증명 승인 방식**    
클라이언트의 자격증명만으로 Access Token을 획득하는 방식이다. 권한 부여 방식 중 가장 간단한 방식이다. Client 자신이 곧 요청의 주체이고 자기 자신의 자격만으로 자기 자신의 권한 범위 안에서 토큰을 받는 구조이다.

# 장점
**비밀번호 비공개** : OAuth 없이 여러 사이트에 같은 비밀번호를 쓰면 **크리덴셜 스터핑(Credential Stuffing)공격**이 가능해진다. OAuth를 쓰면 Client는 애초에 비밀번호를 받아본적도 저장한 적도 없어서 **DB가 털려도 유출될 비밀번호 자체가 없다.**

( **크리덴셜 스터핑이란?** 공격자가 다른 사이트에서 이미 유출된 ID/비밀번호 조합 목록을 확보한 뒤, 이를 여러 사이트에 자동화된 봇으로 대입하며 로그인 성공하는 계정을 찾아내는 공격 )

**Scope로 권한을 문자열 단위까지 쪼갬** : 추상적으로 필요한 만큼만이 아니라 실제로 API마다 Scope 문자열이 세분화돼 있다. 읽기 전용과 전체 권한이 완전히 다른 Scope 값인 것이 그 예시이다.

**검증된 라이브러리 재사용 가능** : RFC6749라는 공통 규격이 있어 검증된 라이브러리(Spring Security OAuth2 Client, NextAuth.js 등)를 그대로 갖다 쓸 수 있다.

( **RFC6749란?** OAuth 2.0의 공식 표준 문서 번호. Grant Type의 정의와 발급 및 교환 절차 등을 규정한 문서 )

# 단점
**Redirect URI/State 검증 실수가 실제 계정 탈취로 직결** : 정확한 redirect_uri 일치가 아니라 접두어 매칭이나 서브 도메인 와일드카드 매칭을 허용하면, 공격자가 등록된 도메인 하위의 오픈 리다이렉터를 끼워 넣어 인증 코드를 자기 서버로 빼돌릴 수 있다.

또 공격자가 인증 코드를 받은 뒤 그 콜백 URL을 피싱 링크나 이미지 태그로 피해자에게 열게 만들면 피해자의 세션에 공격자 외부 계정이 그대로 연결된다. State 값 검증이 없으면 이 요청이 진짜 피해자가 시작한 건지 확인할 방법이 없어서 **CSRF**가 발생한다.

( **CSRF(Cross-Site Request Forgery)란?** 사용자가 이미 로그인된 상태를 악용해서, 공격자가 사용자 모르게 원치 않는 요청을 대신 보내게 만드는 공격 )

**인증 서버 장애 = 서비스 전체 마비** : 소셜 로그인에 의존하는 애플리케이션이라면 구글이나 페이스북 같은 인증 서버가 다운되면 로그인 자체가 불가능해진다. 애플리케이션 서버는 멀쩡해도 외부 인증 서버 하나 때문에 서비스 전체가 마비될 수도 있다.
