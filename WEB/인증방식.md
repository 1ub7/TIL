# Session
**세션(Session)이란?** 일정 시간동안 같은 사용자(브라우저)로부터 들어오는 일련의 요구를 하나의 상태로 보고 **그 상태를 일정하게 유지시키는 기술**이다. 여기서 일정 시간은 방문자가 웹 브라우저를 통해 웹 서버에 접속한 시점으로부터 웹 브라우저를 종료하여 연결을 끝내는 시점을 말한다. 즉, **방문자가 웹 서버에 접속해 있는 상태를 하나의 단위로 본 것**이다.

Session은 **Cookie를 기반**하고 있지만 **서버 측에서 관리**한다. Session에서는 클라이언트를 구별하기 위해 **각 클라이언트에게 고유 ID를 부여**하는데 이 세션 ID로 클라이언트를 구분해서 클라이언트의 요구에 맞는 서비스를 제공하기 때문에 Session은 실제 데이터가 아니라 무작위로 생성된 세션 ID만 쿠키에 담아 클라이언트에 전달하고, 진짜 데이터는 서버에 저장하기 때문에, 쿠키 자체에 개인정보를 직접 담는 방식보다 데이터 노출 위험이 적다.

## Session의 사용 목적
**로그인 상태 유지 :** 최초 로그인 시 발급한 ID를 클라이언트가 매 요청마다 자동으로 함께 보내게 만들어서 사용자가 인증 후 페이지를 이동해도 **로그인 상태를 유지할 수 있게 해준다.**

**사용자별 데이터 임시 저장 :** 회원가입처럼 여러 단계로 나뉜 폼에서 중간 입력값을 임시로 들고 있는 데도 쓰인다. 브라우저를 닫거나 세션이 만료되면 이 데이터는 사라진다. 즉, **사용자 개별 정보를 서버 측에 임시로 저장한다.**  

**보안 및 접근 제어 :** 일정 활동이 없거나 로그인 후 일정 시간이 지나면 세션을 강제로 끊어서 만료시킨다. 아님 즉시 무효화를 시켜서 만료시킨다. 즉, **세션 토큰을 통해 권한 없는 접근을 막고 일정 시간 후 자동 만료를 하며 보안을 강화한다.**

## 장점
**클라이언트에는 의미 없는 값만 노출 :** 클라이언트에 저장되는 건 무작위로 생성된 세션 ID 문자열뿐이고 실제 개인정보·권한 정보는 전부 서버에 저장된다. 그 자체로는 아무 의미도 없고 서버 DB/메모리를 조회해야만 실제 정보에 접근할 수 있다. 

**즉시 무효화 가능 :** 로그아웃 버튼을 누르면 그 순간 해당 세션 데이터를 삭제해버리면 끝이다. 클라이언트가 그 세션 ID를 계속 들고 있어도 서버에 대응하는 데이터가 없으니 그냥 무효한 값이 되는것이다. 

**데이터 용량 제약이 사실상 없음 :** 서버의 메모리나 DB에 저장하는 구조라서 장바구니에 상품 수십 개를 담거나 복잡한 다단계 폼 데이터를 통째로 들고 있어도 클라이언트 쪽 용량 제약에 걸리지 않는다.

## 단점
**서버 확장 시 동기화 문제 :** 서버 메모리에 데이터를 두는 방식이라 서버가 한 대일 때는 문제없지만, 로드밸런서 뒤에 여러 대를 두면 문제가 생긴다. 사용자의 첫 요청이 서버A에 가서 세션이 A에 저장됐는데 다음 요청이 서버B에 가면 B는 그 세션 정보를 모르는 문제가 발생한다.

**서버 자원 소모 :** 동시 접속자 수만큼 세션 데이터를 서버가 계속 들고 있어야한다. 사용자가 많아질수록 메모리 사용량이 커지고 이걸 감당하려고 별도의 세션 저장소를 운영하면 그 자체가 관리해야 할 인프라 구성 요소가 늘어버리는 셈이 된다.

**Cookie 기반이라 Cookie의 한계를 그대로 받음 :** Session은 결국 세션 ID를 Cookie로 실어 나르는 구조라서 쿠키 전송이 까다로운 환경에서는 함께 제약을 받는다.

# Cookie
**쿠키(Cookie)란?** 웹 사이트에 접속할 때 생성되는 정보를 담은 임시 파일이다. HTTP에서 클라이언트의 상태 정보를 클라이언트의 PC에 저장하였다가 필요시 정보를 참조하거나 재사용할 수 있다. 클라이언트 로컬에 저장되며 **키와 값이 들어있는 String 형식의 데이터**이다. 쿠키는 서버에서 **HTTP Response Header**에 **Set-Cookie** 속성을 이용해 클라이언트에 쿠키를 제공한다.

데이터가 서버가 아닌 사용자의 PC에 저장되기 때문에 임의로 고치거나 지울 수 있고 가로채기도 쉬워서 **보안이 취약**하다는 단점이 있다. 즉, **Cookie에는 민감하거나 중요한 정보를 담는 것은 위험하다.**

## Cookie의 사용 목적
**세션 관리(Session Management) :** 서버가 발급한 세션 ID 자체는 쿠키에 담겨서 클라이언트에 전달되고, 이후 매 요청마다 이 쿠키가 자동으로 함께 전송된다. 즉, **세션 ID를 실어 날라 서버가 사용자를 식별할 수 있게 해주는 역할을 한다.**

**개인화(Personalization) :** 로그인 없이도 브라우저를 기억해서 맞춤 경험을 제공하는 용도이다. 로그인 상태 유지 체크박스로 다음 방문 때 자동 로그인시켜주는 것이 그 예시이다. 즉, **각 사용자에게 적절한 페이지를 보여준다.**

**트래킹(Tracking) :** 사용자가 어떤 페이지를 봤는지, 얼마나 머물렀는지, 어떤 상품을 클릭했는지를 기록해서 광고 리타게팅이나 방문 분석에 쓰인다. **사용자의 행동과 패턴을 분석하고 기록하는 용도라고 보면 된다.**

## 보안 속성
**HttpOnly** : JavaScript가 document.cookie로 이 쿠키를 아예 읽을 수 없게 막는다. XSS 공격으로 토큰이 탈취되는 문제가 이 속성으로 방어 가능하다. 공격자가 페이지에 악성 스크립트를 심는 데 성공해도 HttpOnly가 붙은 쿠키는 그 스크립트로 읽어낼 방법이 없다.

( **XSS(Cross-Site Scripting) 공격이란?** 공격자가 신뢰받는 웹사이트에 악성 스크립트를 심어서 그 사이트를 보는 다른 사용자의 브라우저에서 그 스크립트 그대로 실행되게 만드는 공격 )

**Secure** : HTTPS 연결에서만 이 쿠키를 전송하도록 강제한다. 이 속성이 없다면 HTTP 연결에서도 쿠키가 그대로 오가서 같은 와이파이망에 있는 공격자가 패킷을 가로채는 중간자 공격으로 쿠키를 그대로 훔쳐볼 수 있다.

**SameSite :** 다른 사이트에서 시작된 요청에 이 쿠키를 실어 보낼지 말지를 정한다. 앞서 다룬 CSRF 공격을 직접 방어하는 속성이다.

- **Strict :** 다른 사이트에서 온 요청엔 절대 쿠키를 안 싣는다. 가장 안전하지만 외부 사이트 링크로 들어와도 로그인 풀린 거처럼 보이는 불편함이 있다.
- **Lax :** 링크 클릭 같은 단순 이동(GET)은 허용하고, POST 같은 상태 변경 요청엔 안 싣는다.
- **None :** 항상 싣는다. 하지만 반드시 Secure와 함께 써야하고 크로스 도메인 API 통신처럼 의도적으로 필요한 경우에만 사용한다.

**Domain/Path :** 이 쿠키가 어느 도메인·경로에서만 유효한지 범위를 제한한다. Domain=app.com으로 좁혀두면 같은 서버에 있는 다른 서비스로 쿠키가 새어나가는 걸 막을 수 있다.

## 장점
**별도의 설치나 구현 없이 브라우저 표준으로 동작 :** 모든 브라우저가 기본으로 지원하는 기능이라 서버가 Set-Cookie 헤더만 내려주면 그 이후로는 브라우저가 알아서 매 요청마다 자동으로 실어 보낸다. 클라이언트 쪽에서 따로 헤더에 값을 담아 보내는 코드를 짤 필요가 없다.

**만료 기간을 자유롭게 길게 설정 가능 :** Max-Age나 Expires로 몇 시간, 며칠, 몇 달까지도 유지 기간을 정할 수 있어서 '로그인 상태 30일 유지'같은 기능을 브라우저를 꺼도 이어지게 구현할 수 있다.

**서버 자원 부담이 없음 :** 데이터를 클라이언트에 저장하는 구조라서 별도 저장소에 사용자 수만큼의 데이터를 들고 있을 필요가 없다.

## 단점
**보안 속성들을 제대로 설정 안 하면 그대로 취약점이 됨 :** 보안 속성들이 실무에서 하나라도 빠지면 바로 실제 공격 경로가 열리는 필수 설정에 가깝다. 

**용량 및 개수 제한 :** 쿠키 하나당 보통 4KB 안팎, 도메인당 개수도 제한이 있어서 많은 데이터를 담기엔 애초에 적합하지 않은 저장 수단이다. 그래서 실제 데이터는 서버나 클라이언트의 다른 저장소에 두고 쿠키에는 식별자만 담는 방식이 일반적이다.

**매 요청마다 자동 전송되는 게 오히려 오버헤드 :** 이미지, CSS, 폰트 같은 정적 리소스를 요청할 때도 같은 도메인이면 쿠키가 자동으로 함께 실려간다. 딱히 필요 없는 요청에까지 매번 쿠키 데이터가 따라붙어서 쿠키에 담긴 값이 많아질수록 불필요한 트래픽이 누적된다.

# Token
**Token이란?** 서버가 인증된 사용자임을 증명하기 위해 발급하는 문자(또는 데이터)이다. 클라이언트가 이걸 매 요청마다 인증 정보로 함께 실어 보내는 방식이다. Token은 보통 개발자가 직접 HTTP 헤더에 담아 명시적으로 전송한다.

- **Opaque Token(불투명 토큰) :** 그냥 무작위 문자열일 뿐이고 이 문자열 자체엔 아무 정보도 없다. 서버가 이 값을 받으면 DB나 저장소를 조회해서 누구의 토큰인지를 찾아야한다.
- **Self-contained Token(자체 완결형 토큰) :** JWT처럼 토큰 안에 사용자 정보·권한 정보가 그대로 들어있어서, 서버가 서명만 검증하면 별도 조회 없이 바로 인증/인가 처리가 끝난다.

## Token의 사용 목적
**API 인증/인가 :** 서버가 상태를 따로 안 들고 있어도 요청 하나하나에 실린 토큰만으로 이 요청이 누구의 것인지, 어떤 권한이 있는지를 판단할 수 있게 해준다. Session처럼 특정 서버에만 데이터가 남아있는 구조가 아니라서 어느 서버가 요청을 받든 동일하게 처리 가능하다.

**크로스 도메인/플랫폼 인증 :** 모바일 네이티브 앱, SPA, 서드파티에게 제공하는 API처럼 브라우저의 쿠키 저장소가 자연스럽게 동작하지 않는 환경에서 인증을 처리하는 용도이다. 헤더에 값 하나만 실어 보내면 되는 구조라 플랫폼을 가리지 않는다.

**권한 위임 :** OAuth의 Access Token이 대표적인 예시이다. 사용자 본인이 아니라 제3자 애플리케이션이 대신 리소스에 접근할 때 "이 앱은 이 정도 범위(scope)까지만 접근 가능하다"는 제한된 권한을 담아 전달하는 용도로 쓰인다.

## 장점
**서버 확장이 자유로움 :** ( Self-contained 토큰 기준 ) 서버가 세션 데이터를 따로 저장·동기화할 필요가 없어서 "서버 A에 저장된 세션을 서버 B가 모르는 문제"가 애초에 발생하지 않는다. 로드밸런서가 어느 서버로 요청을 보내든 토큰 자체만으로 검증이 끝나기 때문이다.

**크로스 도메인 제약에서 자유로움 :**  Token은 헤더 값 하나라서 정책의 영향을 받지 않는다. 프론트엔드와 API 서버 도메인이 완전히 다른 구조에서도 별도의 CORS 쿠키 설정 없이 헤더만 맞추면 동작한다.

**모바일/네이티브 앱 친화적 :** 브라우저의 쿠키 저장소에 의존하지 않고 앱 자체 저장소(Keychain, EncryptedSharedPreferences 등)에 토큰을 담아 직접 관리할 수 있어서 웹이 아닌 환경에서도 동일한 인증 방식을 그대로 적용할 수 있다.

## 단점
**탈취 시 즉시 무효화가 어려움 :**( Self-contained 계열 ) "이 토큰을 지금 당장 무효로 만들어라"는 명령을 내릴 서버 측 저장소 자체가 없다. 그래서 탈취된 토큰은 만료 시간이 될 때까지 여전히 유효한 게 기본 동작이고 이걸 보완하려면 별도의 블랙리스트(Redis에 폐기된 토큰 목록 관리) 같은 장치를 따로 만들어야 하는데 이러면 Stateless라는 장점이 사라진다.

**저장 위치 고민이 개발자 몫으로 넘어옴 :** Token은 클라이언트가 직접 어딘가에 저장하고 직접 헤더에 실어 보내야 한다. localStorage에 저장하면 XSS 공격에 취약하고 메모리에만 두면 새로고침할 때마다 날아가는 식이다. "어디에 얼마나 안전하게 저장할지"를 개발자가 매번 판단하고 구현해야 하는 부담이 생긴다.

**매 요청마다 헤더에 직접 담아야 하는 구현 부담 :** Token은 프론트엔드 코드에서 API를 호출할 때마다 인증 헤더에 토큰을 직접 넣어주는 로직을 별도로 구현해야 한다. 이 로직이 어느 요청 하나에서 누락되면 그 요청만 인증 실패로 처리되는 실수가 생기기 쉽다.
