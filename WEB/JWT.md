# JWT
**JWT(JSON Web Token)란?** 인증된 유저를 식별하기 위해 가장 일반적으로 사용되는 토큰이다. Header와 Payload가 **JSON 형식**으로 구성되어 있으며, 특정 언어에 종속되지 않는 개방형 표준(RFC 7519)이다. JWT는 인증 서버에서 발급되고, **리소스 서버(API 서버)가 이 토큰을 검증해서 API 접근을 통제**하는 데 가장 많이 사용한다. 주로 클라이언트와 서버 사이에서 정보를 공유하기 위해 사용하는 **개방형 산업 표준**이다.

클라이언트와 서버가 공유할 정보를 JSON에 넣는다. JWT는 이 JSON 객체를 포함한다. 각각의 JWT는 JWT 클레임이라고도 알려진 JSON 컨텐츠가 **클라이언트에 의해 변경되지 않았음을 검증하기 위해 서명(Signature)된다.** 단, 이 서명은 위변조 여부만 확인해줄 뿐 내용 자체를 암호화하는 것은 아니다.

# JWT의 토큰 구성
**Header :** 토큰의 종류와 Signature 생성을 위해서 어떤 알고리즘을 사용했는지 명시된다. 토큰의 유형을 나타내며, HS256(HMAC+SHA256), RS256(RSA+SHA256)과 같은 서명 알고리즘을 나타낸다. ( RSA는 해시가 아니라 비대칭키 서명 알고리즘이다 )      

```json
# 예시
{
    "alg" : "HS256",
    "typ" : "JWT"
}
```

**Payload :** 내가 **로그인한 유저임을 증명**할 수 있는 기본적인 정보들을 삽입한다. 차후에 클라이언트가 다시 토큰을 전송하면 서버는 서명을 검증해서 위변조 여부만 확인하고, 담겨있는 클레임 정보를 그대로 신뢰해서 사용한다. ( DB 조회 없이 처리 가능 ) **Payload에 담는 정보의 한 조각을 클레임(Claim)** 으로 표현하며 이 클레임은 **key-value의 한 쌍**으로 구성된다. 이런 클레임은 여러 개를 삽입할 수 있다.

**등록된 클레임(Registered claims)** : 토큰 정보를 표현하기 위해 이미 JWT표준에 정해진 종류의 데이터들을 의미한다. **보내는 쪽과 받는 쪽이 같은 방식으로 해석**할 수 있다.

**공개 클레임(Public claims)** : JWT의 Payload 부분에 들어가는 정보 중 여러 시스템에서 재사용해도 이름이 충돌하지 않도록, IANA에 등록하거나 URI 형식의 이름으로 정의해서 쓰는 클레임이다. 

**비공개 클레임(Private claims)** : 특정 발급자와 클라이언트끼리만 합의해서 사용하는 **커스텀 클레임**이다. 이름 충돌을 감수하고 자유롭게 정의하는 것일 뿐, '보안 등급이 높다'는 의미는 아니다. JWT는 암호화되지 않으므로 Private claim에도 비밀번호 같은 민감 정보를 넣으면 안 된다.

**서명(signature)** : 인코딩된 **Header**와 **Payload**를 합친 값을 alg에 명시된 알고리즘과 비밀키(혹은 개인키)로 서명해서 만든 값이다. 이 값을 통해 토큰이 발급 이후 변조되지 않았는지 검증할 수 있다. ( 암호화가 아니라 서명이므로, 내용을 숨기는 용도가 아니라 위변조 여부만 확인하는 용도다 )

# 장점
**Stateless 인증 :** 서버가 세션 정보를 별도로 저장할 필요가 없다. **토큰 자체에 필요한 정보가 다 담겨 있어서 서버는 서명만 검증하면 되기 때문**에 서버를 여러 대로 확장해도 세션 동기화 문제가 없다.

**자체 완결성 :** 토큰 안에 사용자 정보, 권한, 만료시간 등의 **클레임(claim)이 담겨 있어서** DB를 추가로 조회하지 않고도 **토큰 자체만으로 인증/인가 처리가 가능**하다.

**크로스 도메인/플랫폼에 유리 :** 쿠키 기반 세션과 달리 헤더에 실어 보내면 되기 때문에 모바일 앱이나 서로 다른 도메인 간 API 통신에서도 제약 없이 쓰기 편하다.

# 단점
**토큰 무효화가 어려움 :** 세션 방식은 서버에서 세션을 지우면 바로 로그아웃 처리가 되는데 JWT는 한번 발급되면 만료시간이 될 때까지 서버가 강제로 무효화하기가 까다롭다.

**페이로드가 노출됨 :** JWT는 암호화가 아니라 서명(base64 인코딩 + signature)만 되어 있어서, 토큰 내용을 디코딩하면 누구나 payload를 읽을 수 있다. 그래서 비밀번호 같은 민감정보를 담으면 안 된다.

**토큰 크기가 커서 매 요청마다 오버헤드 발생 :** 세션 ID는 짧은 문자열 하나만 주고받으면 되는데 JWT는 클레임이 많아질수록 토큰 자체가 커져서 매 요청마다 헤더에 실어 보내는 데이터량이 늘어난다.
