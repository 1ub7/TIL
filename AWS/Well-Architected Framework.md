# Well-Architected Framework
**AWS Well-Architected Framework란?** AWS가 수천 건의 고객 아키텍처를 검토하면서 정리한 클라우드 설계 원칙과 점검 질문 모음이다. 

# 구성 요소
**6개의 Pillar** : 아래에서 설명할 핵심 관점이다.

**Design Principles** : 각 Pillar의 지향점이다.

**Questions & Best Practices** : Pillar별로 10개 안팎의 질문이 있다. 각 질문 아래에 구체적인 모범 사례가 붙어 있다.

**Lenses** : 특정 도메인용 확장판이다.

**Well-Architected Tool** : AWS 콘솔에서 무료로 쓸 수 있는 셀프 리뷰 도구이다. 질문에 답하면 HRI와 MRI를 뽑아준다.

여기서 HRI(High Risk Issue)는 비즈니스에 심각한 부정적 영향을 줄 수 있는 아키텍처 및 운영상의 선택이고, MRI(Medium Risk Issue)는 부정적 영향을 줄 수 있지만 그 정도가 HRI보다 덜한 선택이다.

# 6개의 Pillar

**운영 우수성(Operational Excellence)** : 시스템을 어떻게 운영하고 변화를 어떻게 안전하게 반영하며 실패에서 어떻게 배우는가를 다룬다.

- 운영을 코드로 수행한다. 인프라는 Terraform이나 CloudFormation으로, 배포는 CI/CD로 관리한다.

- 작고 잦고 되돌릴 수 있는 변경을 한다. 한 번에 크게 배포하지 않는다.

- 장애를 미리 예상하고 장애가 나면 포스트모템으로 학습한다.

- 관측 가능성을 갖춘다. 로그, 메트릭, 트레이스가 여기에 해당된다.

**보안(Security)** : 데이터, 시스템, 자산을 보호하고 위협을 탐지·대응하는 능력이다.

- 강력한 자격 증명 기반을 둔다. 최소 권한 원칙을 지키고 장기 자격 증명을 지양하고 IAM Role을 쓴다.

- 추적성을 확보한다. 누가 무엇을 했는지 CloudTrail 같은 도구로 남긴다.

- 사람을 데이터에서 멀리 둔다. 운영자가 프로덕션 DB에 직접 접속하는 구조 자체를 줄인다.

- 전송 중 데이터와 저장 데이터를 모두 암호화한다.

**안정성(Reliability)** : 시스템이 의도한 기능을 일관되게 수행하고 장애에서 회복하는 능력이다.

- 장애를 자동으로 복구한다. healthcheck, Auto Scaling, K8s의 self-healing이 여기에 해당한다.

- 복구 절차를 실제로 테스트한다. 백업만 하고 복원은 한 번도 안 해본 경우가 현업에 생각보다 많다.

- 큰 서버 하나 대신 작은 서버 여러 개로 수평 확장한다.

**성능 효율성(Performance Efficiency)** : 컴퓨팅 리소스를 요구사항에 맞게 효율적으로 사용하고, 수요와 기술이 변해도 그 효율을 유지하는 능력이다.

- 고급 기술을 직접 구축하지 말고 서비스로 소비한다. DB 클러스터를 직접 운영하는 대신 RDS나 Aurora를 쓰는 식이다.

- 서버리스 아키텍처를 활용한다.

**비용 최적화(Cost Optimization)** : 불필요한 비용을 없애고 최소 비용으로 비즈니스 가치를 제공하는 능력이다.

- 클라우드 재무 관리(FinOps) 체계를 갖춘다.

- 쓴 만큼만 내는 모델을 활용한다. 

- 비용의 귀속을 분석한다. 태깅으로 어느 팀, 어느 서비스가 돈을 쓰는지 파악한다.

**지속 가능성(Sustainability)** : 워크로드가 환경에 주는 영향을 최소화하는 것이다. 2021년에 추가되었다.

- 워크로드의 환경 영향을 측정하고 이해한다.

- 리소스 사용률을 극대화한다. 놀고 있는 서버를 줄인다.

- 내용 대부분이 비용 최적화와 겹친다. 비용을 줄이면 환경 영향도 함께 줄어드는 경우가 많다.

# 특징
**정답이 아닌 진단 도구** : 좋은 설계를 알려주는 설계도가 아니라, 질문에 답하면서 내 시스템의 약점을 찾아내는 점검표이다.

**Pillar 간 트레이드오프** : Pillar끼리 서로 충돌한다. 예를 들어 멀티 리전 구성은 안정성을 높이지만 비용이 크게 늘어난다. 어디까지 적용할지는 비즈니스 상황이 결정하며, 보안과 운영 우수성은 일반적으로 타협하지 않는다.

**클라우드 공통 사고방식** : Azure, GCP에도 거의 같은 구조의 프레임워크가 있다. AWS 전용 지식이라기보다 클라우드 설계 전반에 통하는 관점이다.
