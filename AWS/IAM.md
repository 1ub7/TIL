# IAM
**IAM(Identity and Access Management)이란?** AWS에서 사용자, 역할, 정책을 기반으로 리소스 접근을 제어하고 안전한 클라우드 환경을 구축하기 위한 필수 서비스이다.     
(인증+인가 서비스)

사용자의 AWS 리소스에 대한 액세스를 안전하게 제어하는 데 도움이 되는 서비스이다. IAM을 사용하면 AWS 사용자 및 그룹을 생성 및 관리하고 권한을 사용하여 AWS 리소스에 대한 액세스 권한을 부여하거나 거부할 수 있다.

# IAM의 구성요소
## Root User
**AWS 계정을 처음 생성할 때 자동으로 만들어지는 최상위 계정**이다. 계정 생성 시 등록된 이메일 주소로 로그인하며 해당 계정의 모든 AWS 서비스와 리소스에 대해 무제한 권한을 갖게 된다.

Root User만 할 수 있는 작업
- 결제 방식 변경, 요금제 변경
- AWS 계정 자체를 폐쇄
- Reserved Instance 예약 취소
- 특정 서비스 최초 활성화(ex: 특정 리전 최초 사용 설정 등)

## IAM User
**AWS 계정 내에서 만드는 개별 신원이다.** 사람 한 명 또는 특정 애플리케이션 하나에 매핑되는 개념이며 Root User와 달리 관리자가 부여한 권한 범위 내에서만 동작한다.

한 User는 **Access Key를 최대 2개까지 동시 보유가 가능**하다. 이는 키를 교체할 때 기존 키를 바로 폐기하지 않고 새 키 발급을 해서 애플리케이션에 반영을 하고 기존 키 삭제 순으로 **무중단 롤오버**를 하기 위한 설계이다.

User에게 붙는 자격증명 상세
| 구분 | 형태 | 용도 |
|---|---|---|
| 콘솔 로그인 | 사용자명 + 비밀번호 | 웹 콘솔 수동 작업 |
| Access Key | AKIA... (ID) + Secret Key | CLI, SDK, API 프로그래밍 접근 |

Access Key ID는 `AKIA`로 시작하는 20자리 문자열, Secret Key는 40자리 **Secret Key는 발급 시점에만 확인 가능하고 이후 재조회 불가**하므로 분실 시 재발급밖에 답이 없다.

Access Key는 `aws configure` 명령으로 로컬 `~/.aws/credentials`에 저장하거나, 환경변수(`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`)로 주입해서 사용한다.

## IAM Role
**고정된 자격증명이 없는 신원이다.** 대신 누군가 이 Role을 Assume하면 AWS STS가 그 순간에 임시 보안 자격증명을 발급해준다. 이 임시 자격증은 15분~12시간 뒤 자동 만료된다. 

Role의 내부 구성 두 가지
- **Trust Policy(신뢰 정책)** : 누가 이 Role을 Assume할 수 있는지 정의
- **Permission Policy(권한 정책)** : Assume한 뒤 실제로 무엇을 할 수 있는지 정의

**Instance Profile**    
EC2에 Role을 붙일 때는 실제로 Instance Profile이라는 래퍼를 통해 연결된다. Role이 붙은 EC2는 인스턴스 메타데이터를 통해 임시 자격증명을 자동으로 받아오고 SDK가 만료 전 자동 갱신하기 때문에 개발자가 직접 키를 관리할 필요가 없다.

**세션 지속시간 설정**    
Role마다 최소 1시간 ~ 최대 12시간 사이로 임시 자격증명 유효 시간을 지정할 수 있다. 너무 길게 잡으면 탈취 시 피해 시간이 늘어나고 너무 짧으면 장시간 작업(대량 배치 처리 등) 중 자격증명이 만료돼 작업이 끊기는 문제가 생긴다.

**Role Chaining 주의점**    
Role A를 Assume해서 받은 임시 자격증명으로 다시 Role B를 Assume하는 걸 Role Chaining이라 하는데 이 경우 세션 지속시간이 **최대 1시간으로 강제 축소**된다. 여러 단계로 Role을 넘나드는 아키텍처를 설계할 때 자주 걸리는 함정이기도 한다.

## Federated User
**IAM User로 별도 등록되어 있지 않은 외부 신원 공급자(IdP)**를 통해 인증된 사용자가 AWS Role을 Assume해서 접근하는 경우를 가리킨다. 

Federated 인증 방식 두 가지
- **SAML 2.0 기반** : 사내 Active Directory, Okta, Azure AD 같은 기업용 IdP와 연동한다. 주로 동. 주로 **IAM Identity Center(구 AWS SSO)** 를 통해 여러 AWS 계정을 하나의 사내 로그인으로 관리할 때 사용한다.
- **OIDC(OpenID Connect) 기반** : Google, GitHub 같은 **웹 신원 공급자** 혹은 GitHub Actions·Kubernetes ServiceAccount 같은 **기계적 주체**와 연동한다.

# 작동원리
작동 방식은 아래의 순서를 거친다.

```
보안주체(Principal) - 요청(Request) - 인증(Authentication) - 인가(Authorization) - 작업 또는 연산(Action or Operation) - 리소스(Resource)
```

## 보안 주체(Principal)
**보안 주체란?** AWS 리소스에 대한 조치 또는 작업을 수행하도록 요청하는 AWS의 엔터티이다. 주체는 보안 자격 증명을 사용하거나 임시 보안 자격 증명으로 IAM 역할을 가정하여 인증된다.

## 요청(Request)
사용자, 서비스 또는 애플리케이션이 AWS 리소스에 대한 조치 또는 작업을 수행하도록 요청한다. 요청자는 보안 자격 증명(ex: 액세스 키 ID 및 보안 액세스 키)을 사용하거나 임시 보안 자격 증명으로 IAM 역할을 가정하여 인증된다. 

## 인증(Authentication)
보안 주체와 연결된 권한을 확인한다. 이러한 권한은 사용자, 그룹 또는 역할에 연결된 IAM 정책에서 정의된다. 여기서 **정책이란?** 어떤 조건에서 어떤 리소스에 대해 어떤 작업/작업이 허용되거나 거부되는지 지정하는 JSON 문서이다.

## 인가(Authorization)
**인가**는 보안 주체와 연결된 권한을 정의하는 정책을 기반으로 한다. 보안 주체가 AWS 리소스에 대한 작업을 수행하도록 요청하면 IAM은 연결된 정책을 평가해 요청이 허용되는지 또는 거부되는지 결정한다. 최종 승인 결정은 이러한 정책의 조합을 기반으로 한다. 액세스를 명시적으로 거부하는 정책이 있으면 다른 정책에서 허용하더라도 요청이 거부된다. 

## 작업 또는 연산(Action or Operation)
요청 엔터티가 평가된 정책을 기반으로 요청된 작업 또는 연산을 수행할 권한이 있는 경우 IAM은 요청을 진행하도록 허용한다. 그렇지 않으면 IAM이 요청을 거부하고 작업이 수행되지 않는다.

## 리소스(Resource)
요청이 IAM에 의해 승인된 경우 지정된 AWS 리소스에서 작업이 수행된다.

# IAM 정책 유형
## 자격 증명 기반 정책(Identity-based policies)
**IAM 사용자, 그룹 또는 역할에 연결된 정책**이다. IAM 자격 증명이 수행할 수 있는 작업, 액세스할 수 있는 리소스 및 관련 조건을 제어한 자격 증명 기반 정책은 아래 두가지로 또 나뉜다.

**관리형 정책**
독립된 개체로 존재하는 정책이다. 여러 User/Group/Role에 **재사용 가능**하고 하나 수정하면 그 정책이 부착된 모든 대상에 동시 반영된다. 관리 주체에 따라 다시 둘로 나뉜다.

- **AWS 관리형 정책(AWS Managed Policy)**: AWS가 만들고 관리하는 정책이다. `AmazonS3ReadOnlyAccess`, `AdministratorAccess`처럼 이름에 서비스명이 들어간다. 내가 수정할 수 없고 AWS가 새 API를 추가하면 자동으로 업데이트된다. 바로 갖다 쓸 수 있어서 편하지만 범위가 넓게 잡혀있는 경우가 많아 최소 권한 원칙에는 잘 안 맞을 때가 많다.

- **고객 관리형 정책(Customer Managed Policy)**: 사용자가 직접 JSON을 작성하거나 AWS 관리형 정책을 복제해서 만드는 정책이다. 여러 User/Group/Role에 재사용 가능하고 **버전 관리(최대 5개 버전 저장, 이전 버전으로 롤백 가능)** 를 지원한다.

**인라인 정책**
특정 **User, Group, Role 단 하나에만 직접 내장(embed)** 되는 정책. 관리형 정책과 달리 독립된 개체로 존재하지 않고 그 대상에 완전히 종속된다.

- **재사용 불가**: 다른 User/Role에 똑같이 붙이고 싶으면 정책 내용을 복사해서 새로 만들어야 한다.
- **생명주기가 대상과 동일**: 그 User나 Role을 삭제하면 인라인 정책도 함께 삭제된다. (관리형 정책은 대상이 삭제돼도 정책 자체는 독립적으로 남는다)
- **1:1 관계가 명확할 때만 권장**: "이 Role 하나에만 필요한 다른 곳엔 절대 쓰이지 않을 특수 권한"처럼 예외적인 경우에 한정해서 사용하는 게 좋다.

## 리소스 기반 정책(Resource-based policies)
**S3 버킷, SQS 대기열 또는 KMS 키와 같은 AWS 리소스에 연결된 정책이다.** 리소스에 액세스할 수 있는 IAM 자격 증명과 수행할 수 있는 작업을 정의한다. 

이러한 정책은 자격 증명 기반 정책을 수정하지 않고 특정 리소스에 대한 교차 계정 액세스 권한을 부여해야 할 때 유용하게 사용한다.

## 권한 경계(Permissions boundaries)
**IAM 엔터티(사용자 또는 역할)가 가질 수 있는 최대 권한을 설정**하는 데 사용되는 고급 IAM 기능이다. IAM 엔터티에 연결하는 정책이며 경계 역할을 하여 더 많은 허용 정책이 연결되어 있더라도 엔터티에 부여된 권한을 제한한다. 

권한 경계는 부여할 수 있는 최대 권한에 대한 제어를 유지하면서 다른 사용자에게 **IAM 권한 관리를 위임**하려는 경우에 유용하다.

## 조직 SCP
SCP는 **조직 또는 특정 조직 단위 내의 모든 계정에 대한 권한을 정의**하기 위해 AWS Organizations에서 사용되는 정책이다. 가드레일 역할을 하여 조직 내에서 액세스할 수 있는 작업과 리소스를 제한한다. 

IAM 자격 증명에 더 많은 허용 정책이 연결되어 있어도 마찬가지이다. SCP는 **조직 정책 및 액세스 제한이 모든 AWS 계정에서 일관되게 적용**되도록 한다.

## 액세스 제어 목록(ACL)
S3 버킷 및 객체와 같은 **특정 AWS 리소스에 대한 액세스를 제어하는 데 사용되는 레거시 정책**이다. 여전히 사용할 수 있지만 AWS는 일반적으로 보다 세분화된 액세스 제어 및 관리 용이성을 위해 리소스 기반 정책 또는 자격증명 기반 정책을 사용할 것을 권장한다.

## 세션 정책
**역할의 임시 자격 증명 권한을 제한하려는 경우에 사용되는 고급 정책**이다. AWS STS를 사용하여 역할을 수임할 때 선택적 세션 정책을 전달해 역할의 권한 정책에서 부여하는 권한을 추가로 제한할 수 있다.

# 특징
**전역 서비스** : IAM은 특정 리전에 종속되지 않는 **전역(Global) 서비스**이다. AWS 콘솔 우측 상단의 리전 선택 드롭다운은 EC2, RDS, S3 같은 **리전형 서비스**에만 영향을 주고, IAM 화면은 어느 리전을 선택하든 항상 동일한 화면과 동일한 데이터를 보여준다. 서울 리전에서 만든 User든 버지니아 리전에서 만든 User든 모든 리전의 리소스에 동일하게 적용되며, IAM 관련 API 엔드포인트도 리전 코드 없이 전역으로 고정되어 있다.

**Federation을 통한 확장성** : IAM은 자체 User를 계정 안에 일일이 만들지 않아도 **외부 신원 공급자(IdP)를 신뢰하는 방식**으로 접근을 허용할 수 있다. 이를 Federation(연합 인증)이라 부르며 IAM의 확장성을 만드는 핵심 특징이다. 사내 Active Directory·Okta 같은 SAML 기반 IdP나, GitHub Actions·Kubernetes ServiceAccount 같은 OIDC 기반 기계적 주체 모두 이 방식으로 연동 가능하다. 조직 규모가 커져도 IAM User를 계정마다 개별 생성할 필요 없이 중앙 IdP 하나로 접근을 통합 관리할 수 있다는 게 이 특징의 실질적 이점이다.

**기본값을 거부함(Default Deny)** : 새로 만든 IAM User나 Role은 **아무 정책도 붙어있지 않으면 그 어떤 API 호출도 수행할 수 없는 상태**로 시작한다. 콘솔 로그인은 되지만 화면에 리소스 목록조차 하나도 안 뜨는 상태 (이게 IAM의 출발점). "일단 다 열어놓고 위험한 것만 막는" 블랙리스트 방식이 아니라 "일단 다 막아놓고 필요한 것만 여는" 화이트리스트 방식이며, 이 원칙이 최소 권한 원칙(Least Privilege) 설계의 출발점이 된다. 단, Root User는 이 규칙의 유일한 예외로, 정책 없이도 처음부터 모든 권한을 가진다.

**명시적 거부 최우선(Explicit Deny Overrides)** : 정책 평가는 `Explicit Deny > Explicit Allow > Implicit Deny(기본값)` 순서로 이뤄진다. Identity Policy, Resource Policy, Permission Boundary, SCP 등 여러 정책이 동시에 적용될 때, 그중 단 하나라도 명시적으로 `Deny`가 걸려 있으면 다른 곳에서 아무리 `Allow`를 부여해도 최종 결과는 거부로 확정된다. 이 특징 때문에 실무에서는 "왜 권한을 줬는데 안 되지?"를 디버깅할 때, Allow가 부족한 건 아닌지뿐 아니라 어딘가에 숨어있는 Deny가 있는지도 함께 확인해야 한다.

# 장단점
## 장점
**중앙 집중식 접근 관리** : AWS 계정 하나에 사람이 수십 명, 수백 명이 있어도 User·Group·Role·Policy를 하나의 콘솔/API에서 전부 생성·수정·삭제·조회할 수 있다. 서버마다 개별 계정을 만들고 서버마다 따로 비밀번호를 관리하던 방식과 비교하면 IAM은 "누가 무엇에 접근 가능한지"를 한 곳에서 파악하고 통제할 수 있게 해준다. 퇴사자가 생기면 그 User 하나만 비활성화해도 모든 리소스 접근이 동시에 차단되고, 여러 AWS 계정을 운영하는 조직이라면 IAM Identity Center로 계정 여러 개를 하나의 로그인 지점으로 통합해서 관리 부담을 더 줄일 수 있다.

**세분화된(Granular) 권한 제어** : 
IAM 정책은 서비스 단위(`s3:*`)뿐 아니라, **API 단위**(`s3:GetObject`만 허용하고 `s3:DeleteObject`는 거부), **리소스 단위**(특정 버킷의 특정 폴더만), **조건 단위**(특정 IP 대역에서만, MFA 인증한 경우에만, 특정 시간대에만, 특정 태그가 붙은 리소스에만)까지 정밀하게 권한을 쪼갤 수 있다. 이게 최소 권한 원칙을 실제로 구현 가능하게 만드는 수단이며, 예를 들어 CI/CD 배포용 Role을 "특정 버킷에 업로드만 가능, 삭제는 불가능"하게 좁혀두면 자격증명이 탈취되더라도 피해 범위가 그 좁은 권한 안으로 제한된다.

**임시 자격증명 기반 위임** : 
IAM Role은 고정된 Access Key 없이 **STS가 그때그때 발급하는 임시 자격증명**으로 동작한다. 이게 IAM의 가장 실무적인 강점 중 하나로 꼽히는 이유는 장기 고정 키를 아예 존재하지 않게 만들어서 유출 자체가 구조적으로 어려워지기 때문이다. EC2/Lambda에 Role을 붙이면 코드나 환경변수 어디에도 Access Key가 존재하지 않고, 발급된 자격증명도 최소 15분~최대 12시간 뒤 자동 만료되므로 어딘가에 로그로 남아도 피해 범위가 제한된다.

## 단점
**디버깅과 원인 추적이 매우 어렵다** : 
IAM에서 접근이 거부되면 반환되는 에러는 대부분 그냥 **`AccessDenied` 한 줄**이다. "정확히 어떤 정책의 어떤 Statement가 이 요청을 막았는지"는 에러 메시지에 나오지 않는다. Identity Policy, Resource Policy, Permission Boundary, SCP, Session Policy까지 최대 5중으로 정책이 겹칠 수 있는 구조에서 사람이 하나하나 수동으로 확인해야 원인을 찾을 수 있다. Policy Simulator나 Access Analyzer 같은 보완 도구가 있지만, 이것도 "가능성 있는 원인을 하나씩 점검하는" 도구이지 원인을 바로 알려주는 도구는 아니다.

**과다 권한 부여(Over-permissioning)로 흐르기 쉬운 구조적 유혹** : 
IAM은 세분화된 권한 제어가 가능하다는 장점이 있지만 역설적으로 **실무 압박 속에서는 그 반대 방향으로 흘러가기 쉽다**. "일단 되게 만들자"는 압박 아래 `AdministratorAccess`나 `*:*` 같은 광범위한 정책을 임시로 붙이고 그게 "임시"로 끝나지 않고 그대로 방치되는 경우가 매우 흔하다. 세밀한 정책을 짜려면 서비스의 정확한 API 범위를 미리 파악하는 시간이 드는 반면, 넓은 정책은 즉시 문제를 해결해주기 때문에 시간에 쫓기는 환경일수록 이 유혹이 커진다.

**정책이 코드가 아니라 JSON 문서라서 생기는 취약성** : 
IAM 정책은 프로그래밍 언어가 아니라 **JSON 문서**이기 때문에 문법 오류나 논리 실수가 나도 컴파일러처럼 잡아주는 도구가 기본적으로 없다. 괄호 하나, 쉼표 하나, `Resource` ARN의 와일드카드 위치 하나로 의도와 완전히 다른 정책이 만들어질 수 있다. 특히 **구문은 완벽한데 의미가 틀린 경우**(의도보다 훨씬 넓은 권한을 허용하는 경우)는 배포 시점엔 아무 문제 없이 통과되고 나중에 보안 사고나 감사 때야 발견되는 경우가 많아서 Terraform 같은 IaC로 정책을 코드화하고 `tfsec`/`checkov` 같은 정적 분석 도구로 사전 검증하는 흐름이 표준화되고 있다.
