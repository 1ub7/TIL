# Route Table
**Route Table이란?** VPC 내에서 트래픽이 어디로 가야 할지를 결정하는 규칙들의 집합이다. 서브넷 단위로 연결되며 **"이 목적지 대역으로 가는 트래픽은 이 타겟으로 보내라"** 는 규칙들의 테이블이다.

IGW랑 NAT Gateway도 전부 **Route Table을 거쳐서 작동하는 구조**이다.

# 역할
**목적지-타겟 매핑** : 각 규칙은 **Destination(목적지 CIDR) + Target(보낼 대상)** 으로 구성된다. 트래픽이 나갈 때 이 테이블을 보고 목적지 대역과 가장 정확히 일치하는 규칙을 타고 나간다.

**서브넷과의 연결** : 라우팅 테이블 자체는 독립적으로 존재하고 서브넷에 연결해야 그 서브넷에 적용된다. 하나의 라우팅 테이블을 여러 서브넷에 연결할 수 있고 반대로 **서브넷 하나는 반드시 하나의 라우팅 테이블에만 연결**된다.

**Local 라우트는 자동 생성** : VPC를 만들면 `VPC CIDR -> Local` 규칙이 자동으로 들어가 있다. Route Table이 있어서 **VPC 안의 서브넷끼리는 별도 설정 없이 서로 통신 가능**한 것이다.     
(이 규칙은 삭제 불가)

# 특징
**메인 라우트 테이블 VS 커스텀 라우트 테이블** : VPC를 생성하면 **기본으로 메인 라우트 테이블이 하나 자동 생성**된다. 서브넷을 새로 만들면 명시적으로 다른 테이블을 지정하지 않는 한 자동으로 이 메인 테이블에 연결된다. 

실무에서는 보통 메인 테이블은 그대로 두거나 프라이빗용으로 쓰고 퍼블릭 서브넷용으로 **커스텀 라우트 테이블을 따로 만들어서 IGW 규칙을 넣는 식**으로 분리해서 관리한다.

**가장 구체적인 규칙이 우선** : 라우팅 테이블에 `0.0.0.0/0`이랑 `10.0.1.0/24`가 동시에 있으면 목적지가 `10.0.1.5`인 트래픽은 후자를 따라간다.

**퍼블릭/프라이빗 서브넷 구분의 실체** : 그 서브넷에 연결된 라우팅 테이블에 `0.0.0.0/0` 규칙이 있냐 없느냐로 결정된다. 즉, **Route Table이 퍼블릭/프라이빗을 가르는 실질적 기준이다.**

# 장단점
## 장점
**트래픽 흐름을 명시적으로 통제 가능** : 어떤 서브넷이 어디로 나갈지를 **라우팅 테이블 설계만으로 세밀하게 제어 가능**하다. 서브넷별로 다른 라우팅 테이블을 붙여서 서로 다른 네트워크 정책 적용이 가능하다.

**서브넷 간 재사용 가능** : 하나의 라우팅 테이블을 여러 서브넷에 연결할 수 있어서 **똑같은 라우팅 정책을 쓰는 서브넷들은 테이블 하나로 관리 가능**하다.     
(중복 설정을 안 해도 됨)

**별도 리소스 비용 없음** : 라우팅 테이블 자체는 무료이고 규칙 추가/삭제하면 바로 적용된다. 

## 단점
**설정 실수가 바로 장애/보안사고로 이어짐** : 라우팅 규칙 하나 잘못 넣으면 그 즉시 프라이빗 리소스가 인터넷에 노출되거나 반대로 **필요한 규칙을 빼먹으면 통신 자체가 끊긴다.** 

**어떤 라우팅 테이블이 어느 서브넷에 붙어있는지 추적 어려움** : 서브넷이 많아지고 커스텀 라우팅 테이블이 여러 개 생기면 "이 서브넷이 지금 어느 테이블에 연결돼 있고, 그 테이블엔 무슨 규칙이 있는지" 파악하는 게 헷갈리기 시작한다.

**규칙 개수 제한 존재** : 라우팅 테이블 하나당 등록 가능한 라우트 개수에 기본 할당량이 있다. 기본이 50개이지만 네트워크가 복잡해지면 이 한도에 걸릴 수 있어서 대규모 설계 시 고려 대상이다.
