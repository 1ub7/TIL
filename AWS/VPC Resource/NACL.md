# NACL
**NACL(Network Access Control Lists)란?** 네트워크 ACL(액세스 제어 목록)은 트래픽을 제어하는 방화벽 역할을 수행한다. **서브넷**이라는 넓은 범위에 적용되는 방화벽으로 해당 서브넷에 존재하는 모든 자원에게 공통의 방화벽 Rule을 관리하고자 하는 경우에 유용하다.

서브넷 전체에 적용된다. 하나의 서브넷에 있는 모든 리소스는 그 서브넷에 연결된 NACL 규칙을 똑같이 받는다. VPC를 만들면 Default NACL이 자동으로 하나 생기고 **모든 서브넷은 최소 하나의 NACL에 연결되어 있어야 한다.** Custom NACL을 만들어서 특정 서브넷에만 별도로 붙일 수도 있다.

# 특징
**적용 단위가 서브넷** : NACL은 SG와 다르게 인스턴스(ENI)가 아니라 **서브넷 자체**에 적용된다. 그래서 같은 서브넷 안에 있는 모든 리소스(EC2, RDS 등)는 개별 설정과 무관하게 그 서브넷에 연결된 NACL 규칙을 동일하게 적용받는다. Custom NACL을 만들어서 특정 서브넷에만 더 엄격한 규칙을 적용하는 것도 가능하지만 서브넷 하나에는 NACL이 하나만 연결될 수 있다.

**무상태(Stateless)** : SG는 Stateful이라 인바운드를 허용하면 그 연결의 응답이 자동으로 나갔지만 NACL은 그런 게 없다. 인바운드 규칙과 아웃바운드 규칙이 완전히 독립적으로 평가되기 때문에 요청이 들어오는 방향과 응답이 나가는 방향을 **각각 따로 명시적으로 열어줘야** 한다. 

특히 여기서 중요한 게 **임시 포트(Ephemeral Port)** 문제인데 클라이언트는 서버에 요청을 보낼 때 자기 쪽에서 랜덤한 포트(보통 1024~65535 범위)로 응답을 받기 때문에 서버 쪽 아웃바운드 규칙에 이 임시 포트 범위 전체를 열어주지 않으면 서버가 응답을 만들어도 클라이언트한테 도달하지 못한다. 그래서 NACL을 설정할 때 인바운드만 신경 쓰고 아웃바운드를 소홀히 하면 요청은 들어오는데 응답이 안 나가서 연결이 끊기는 것처럼 보이는 상황이 생기고 이게 NACL 트러블슈팅에서 가장 흔하게 걸리는 함정이다.

**Allow+Deny 둘 다 가능** : SG는 허용 규칙만 만들 수 있는 구조라서 특정 IP 하나만 콕 집어서 차단하는 게 원천적으로 불가능했다. 반면 NACL은 규칙 하나하나에 Allow와 Deny를 명시적으로 지정할 수 있어서 특정 IP나 CIDR 대역을 정확히 지목해서 차단하는 게 가능하다. 

이때 주의할 점은 NACL이 Rule Number 순서대로 평가되기 때문에, Deny 규칙을 Allow 규칙보다 **더 낮은 번호(더 먼저 평가되는 위치)** 에 둬야 실제로 차단이 먹힌다는 것이다. 만약 광범위한 Allow 규칙이 먼저 평가되고 그 뒤에 Deny를 걸어두면, 이미 앞에서 매칭되어버렸기 때문에 뒤에 있는 Deny는 평가조차 되지 않는다. 

# 규칙 구성 요소
항목 | 설명
--- | ---
Rule Number | 규칙 번호 (평가 순서를 결정)
Type | 프로토콜 프리셋
Protocol | TCP/UDP/ICMP
Port Range | 포트
Source/Destination | CIDR 블록만 가능 (SG 참조 불가능)
Allow / Deny | 허용할지 차단할지 명시

## Rule Number 평가 방식
번호가 낮을수록 먼저 평가되고 매칭되면 그걸로 끝이다. 뒤에 더 관대한 규칙이 있어도 소용이 없다. 세밀한 예외를 두고 싶으면 그 규칙을 더 낮은 번호로 앞에 배치해야 한다.

예시
```
Rule 100: DENY  192.168.1.100/32  ALL TRAFFIC
Rule 200: ALLOW 0.0.0.0/0         80, 443
Rule *  : DENY  0.0.0.0/0         ALL TRAFFIC (기본 규칙, 항상 마지막)
```

마지막에 있는 `*` 규칙은 와일드카드 규칙이라고 부르고 명시된 **어떤 규칙에도 안 걸린 트래픽은 전부 여기서 차단된다.**

# 장단점
## 장점
**Deny 규칙으로 특정 IP를 정교하게 차단할 수 있음** : SG는 Allow만 가능해서 악성 IP 하나를 막으려 해도 방법이 없었는데 NACL은 **Rule Number 순서와 조합해서 특정 IP나 CIDR 대역을 콕 집어 차단**할 수 있다. DDoS나 반복 공격 시도가 들어올 때 서브넷 레벨에서 즉각 대응할 수 있는 유일한 수단이다.

**서브넷 단위로 일괄 적용되기 때문에 일관된 정책을 강제하기 쉬움** : 개별 인스턴스마다 SG를 따로 설정하다 보면 실수로 하나만 빠뜨리는 경우가 생기는데 NACL은 서브넷에 속한 모든 리소스에 동일하게 적용되므로 **"이 서브넷 안에 있는 건 전부 이 규칙을 따른다"**는 걸 보장할 수 있다. 

**SG가 뚫려도 2차 방어선 역할을 할 수 있음** : SG 설정 실수로 원치 않는 포트가 열렸더라도 NACL에서 서브넷 레벨로 한 번 더 걸러주면 실제 피해로 이어지기 전에 막을 여지가 생긴다. 방어 계층을 하나 더 두는 셈이라서 보안 설계 관점에서 안전판 역할을 한다.

## 단점
**운영 부담이 SG보다 훨씬 큼** : 인바운드/아웃바운드를 항상 양쪽 다 신경 써야하고 특히 **임시 포트 범위를 안 열어주면 요청은 들어오는데 응답이 안 나가는 상황이 생긴다.** 이런 문제는 원인 파악이 까다로워서 트러블슈팅에 시간이 많이 든다.

**Rule Number 순서를 잘못 설계하면 의도한 대로 동작하지 않음** : 매칭되는 규칙을 만나는 즉시 평가가 끝나버리기 때문에 광범위한 규칙을 낮은 번호에 **실수로 배치하면 그 뒤에 있는 세밀한 예외 규칙이 아예 평가조차 안 된다.** 규칙이 늘어날수록 번호 순서를 관리하는 자체가 부담이 된다.

**SG 참조가 안 되고 CIDR 기반이라 동적 인프라에 취약** : **NACL는 오직 IP 대역으로만 지정 가능**하다. 오토스케일링처럼 IP가 계속 바뀌는 환경에서는 NACL 규칙을 IP 기반으로 유지보수하기가 번거롭고 그래서 실무에선는 세밀한 제어를 SG한테 맡기고 NACL은 **광범위한 차단 용도**로만 최소한으로 쓰는 경우가 많다.
