# NAT Gateway
**NAT Gateway란?** 프라이빗 서브넷의 리소스가 인터넷으로 나갈 수 있게 해주는 AWS 관리형 NAT 서비스이다. 프라이빗 IP를 가진 인스턴스가 아웃바운드 통신은 하되 외부에서 먼저 들어오는 요청은 막아야 할 때 쓴다.

반드시 **퍼블릭 서브넷**에 위치해야 하고 자기 자신은 인터넷 통신을 위해 EIP를 하나 물고 있어야 한다.

# 역할
**다대일 NAT** : 여러 개의 프라이빗 IP를 NAT Gateway가 가진 하나의 퍼블릭 IP로 매핑해서 내보낸다. 외부 입장에서는 다 같은 IP에서 나오는 것처럼 보인다. 

**라우팅 대상 역할** : 프라이빗 서브넷의 라우팅 테이블에 `0.0.0.0/0` 규칙을 등록해야 한다. 참고로 **NAT Gateway 자체는 퍼블릭 서브넷**에 있지만 **라우팅 규칙은 프라이빗 서브넷** 쪽에서 걸러주는 것이다.

# 특징
**트래픽 단방향** : 프라이빗 리소스가 먼저 나가는 트래픽만 허용하고 외부에서 먼저 개시하는 인바운드 요청은 차단된다. 정확히는 **아웃바운드로 나간 트래픽에 대한 응답만** 돌아올 수 있는 구조이다.

**AZ 종속 리소스** : NAT Gateway는 특정 AZ 안에 생성된다. 그래서 그 AZ가 죽으면 그 NAT Gateway도 같이 못 쓴다. 고가용성 확보하려면 결국 AZ 개수만큼 만들어야 하는데, 이게 아래 "비용 부담" 항목으로 이어진다.
(라우팅 자체가 AZ 경계를 못 넘기 때문에 안된다.)

**대역폭 상한 존재** : Gateway 하나당 처리량 한도가 있다. 트래픽이 많으면 병목이 생길 수 있어서 설계할 때 고려해야 한다.

# 장단점
## 장점
**프라이빗 리소스 보안 확보** : 외부에서 직접 접근하면 안 되는 리소스도 아웃바운드는 필요한 경우가 많은데 이걸 인터넷에 노출 안 시키고 해결해준다.

**AWS 관리형** : NAT Instance와 다르게 AWS가 관리해줘서 처리량도 자동 스케일링이 돼서 패치나 장애 복구에 신경을 안 써도 된다. 

**설정 단순** : 퍼블릭 서브넷에 생성하고 EIP 연결한 다음에 프라이빗 서브넷 라우팅 테이블에 등록하면 된다.

## 단점
**대역폭 한도 존재** : 트래픽 몰리는 서비스라면 NAT Gateway 자체가 병목이 될 수 있다. 이럴 땐 여러 개로 분산하거나 트래픽 패턴 자체를 재설계해야 한다.

**AZ 장애에 취약** : AZ 하나에만 만들어두면 그 AZ 죽었을 때 그 안의 프라이빗 리소스가 전부 아웃바운드 통신 불가 상태가 된다. 고가용성 확보하려면 결국 AZ 개수만큼 만들어야 하는데 이게 위 비용 문제로 이어진다.

**비용 부담** : 이중 과금 구조라 트래픽이 특히 많은 환경에서는 생각보다 비용이 크게 나간다. 고가용성 확보하려고 AZ마다 만들면 비용도 그만큼 배로 늘어나서 실무에서는 비용-가용성 트레이드오프 판단을 항상 하게 된다.
