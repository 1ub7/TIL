# IGW
**IGW(Internet Gateway)란?** VPC와 인터넷 사이를 연결해주는 관문 역할을 하는 AWS 리소스이다. 물리 장비가 아닌 논리적 컴포넌트이고 VPC 하나당 하나씩만 붙일 수 있다.

기본적으로 VPC는 인터넷과 격리되어 있기 때문에 외부와 통신하려면 **인터넷으로 나가는 통로**가 필요하고 그 역할이 IGW가 된다.

# 역할
**라우팅 대상** : 라우팅 테이블에 `0.0.0.0/0`을 IGW로 등록하면 해당 서브넷 인터넷 통신이 가능하게 해준다. 이 규칙이 있는 서브넷은 **퍼블릭 서브넷**과 같다.

**NAT 역할** : **1:1 NAT 방식**으로 EC2의 프라이빗 IP ↔ 퍼블릭 IP 매핑 처리를 해준다. EC2에 퍼블릭 IP/EIP 할당을 해도 인스턴스 자체는 프라이빗 IP만 갖고 있어서 IGW가 중간에서 변환해준다. 

NAT Gateway는 여러 개의 프라이빗 IP를 하나의 퍼블릭 IP로 묶는 다대일 NAT라 아웃바운드만 가능하지만 IGW는 인스턴스별로 1:1 매핑을 하기 때문에 양방향이 가능한 것이다.

# 특징
**트래픽 양방향** : 인바운드 규칙과 아웃바운드 규칙 둘 다 허용한다. 외부에서 먼저 요청을 걸어도 통과가 가능하다. 웹서버가 퍼블릭 서브넷에 있는 이유가 이 양방향 특성 때문이다.

**가용성** : 특정 AZ에 종속되지 않는 VPC 레벨 리소스이다. AWS 관리형이라 별도 이중화가 불필요하고 한 AZ 문제로 영향을 받지 않는다. attach/detach 가능하지만 동시에 여러 VPC에 붙일 수는 없다.

**처리량 제한 없음** : 대역폭/처리량에 별도 상한 없이 AWS가 자동 스케일링을 한다. 분산 설계가 필요하지 않고 한도 제약이 없다.

# 장단점
## 장점
**구성 단순** : VPC에 IGW 하나 생성해서 연결하고 라우팅 테이블에 `0.0.0.0/0` 규칙 하나만 추가하면 설정이 끝난다. VPC 레벨에서 한 번 설정하면 된다.

**비용 부담 적음** : IGW 자체는 생성/연결/사용에 요금이 전혀 없다. 발생하는 비용은 전부 아웃바운드 데이터 전송량에 대한 표준 AWS 데이터 전송 요금이다.

**관리 부담 없음** : AWS가 완전 관리형으로 운영해서 이중화, 장애 복구, 패치 같은 걸 사용자가 신경 쓸 필요가 없다. 처리량 상한도 없어서 트래픽이 늘어나도 별도 스케일업/스케일아웃 작업이 필요하지 않다.

## 단점
**보안 리스크 직결** : 양방향 통신이 가능하다는 특성은 설정 실수가 즉시 외부로 노출될 수 있다는 뜻이기도 한다. 보안그룹에서 `0.0.0.0/0`으로 특정 포트를 열어두면 바로 전세계에서 접근 가능한 상태가 되는 경우가 그 예시이다.

**세밀한 접근 제어 불가** : IGW는 인터넷으로 트래픽을 내보내고 받아들일지 말지를 결정하는 게이트웨이 역할만 한다. 특정 IP만 허용하거나 포트를 필터링하는 기능이 없기 때문에 실제 접근 제어는 별도 계층에서 처리해야 한다. 

**프라이빗 리소스에는 못 씀** : IGW의 구조상 퍼블릭 IP를 가진 리소스와의 양방향 통신을 위한 것이라서 애초에 퍼블릭 IP 자체를 받지 않는 DB 서버 같은 리소스에는 적용할 대상이 없다. 이런 리소스가 패치 다운로드나 외부 API 호출처럼 아웃바운드만 필요하면 NAT Gateway를 별도로 구성해야 한다.
