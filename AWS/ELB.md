# ELB
**ELB(Elastic Load Balancer)란?** 단일 또는 여러 가용 영역에서 다양한 애플리케이션의 부하를 처리할 수 있는 로드 밸런싱을 제공하는 서비스이다.   
(즉, 클라이언트 요청을 여러 대상으로 분산시켜서 트래픽 처리를 하는 것)

확장성과 고가용성을 지원하기 위한 서비스로서 **인스턴스로 들어오는 트래픽을 관리해주는 역할**이다. 자체적으로 로드 밸런서를 마련하는 것보다 훨씬 저렴하며 확장성도 뛰어나다.

## 로드 밸런싱(Load Balancing)
**로드 밸런싱(Load Balancing)란?**  들어오는 트래픽을 여러 대의 서버에 나눠서 분산시키는 기술을 말한다. 주로 하는 역할은 아래와 같다.

**분산(Distribution)** : 요청을 어떤 규칙으로 여러 서버에 나눠준다.

**헬스체크(Health Check)** : 서버들이 살아있는지 계속 확인하다가 죽은 서버는 트래픽을 안보내고 제외시킨다. 

# 종류
| 종류 | 계층 | 기본 분산 알고리즘 | 언제 쓰나 |
|---|---|---|---|
| **ALB(Application LB)** | L7 (HTTP/HTTPS/WebSocket) | Least Outstanding Requests (처리 중인 요청 적은 대상 우선) | URL 경로/도메인 기반 라우팅 필요할 때, 컨테이너(ECS/EKS) 환경 |
| **NLB(Network LB)** | L4 (TCP/TLS/UDP) | Flow Hash (연결 단위 해싱) | 초저지연·고성능, 고정 IP 필요할 때, gRPC |
| **CLB(Classic LB)** | L4/L7 혼합 | Round Robin | 레거시. 신규 구축엔 사용 안 함 |
| **GWLB(Gateway LB)** | L3 | - | 방화벽/IDS 같은 보안 어플라이언스 앞단 트래픽 검사용 |

# 역할
**트래픽 분산** : 들어오는 요청을 여러 인스턴스 및 컨테이너로 알고리즘에 따라 나눠준다. (ALB는 Least Outstanding Requests, NLB는 Flow Hash 방식을 기본으로 사용)

**헬스체크 & 장애 대상 자동 제외** : 주기적으로 대상한테 요청을 보내서 응답을 확인한다. 실패 임계값 넘으면 그 대상을 트래픽 분산 대상에서 즉시 제외한다. 아래는 ALB 기본값 기준 표이다.

| 항목 | 기본값 |
|---|---|
| Interval (체크 주기) | 30초 |
| Timeout | 5초 |
| Healthy threshold | 연속 5회 성공 |
| Unhealthy threshold | 연속 2회 실패 |
| 체크 경로 | `/` |

(기본 경로 `/`는 프로세스가 살아있는지만 확인하지 DB 연결 같은 실제 의존성 장애는 못 잡는다. 그래서 실무에서는 `/health` 같은 별도 엔드포인트를 만들어서 DB/캐시 연결까지 체크하게 구성하는 경우가 많다.)

**고가용성 확보(메커니즘 관점)** : 헬스체크로 죽은 대상을 자동 제외하고 여러 AZ로 분산하기 때문에 서버 한 대(혹은 AZ 하나)가 죽어도 서비스 중단 없이 SLA(가용성 목표치, 예 99.9%)를 유지할 수 있다.

**SSL/TLS 종료 (SSL Termination)** : 클라이언트-ELB 구간만 HTTPS로 암호화하고 ELB-백엔드 구간은 HTTP 평문으로 통신하도록 설정이 가능하다. 백엔드 서버는 암호화 연산 부담 없이 로직 처리에만 집중할 수 있다.

**경로/도메인 기반 라우팅 (ALB 한정, L7)** : 하나의 ALB로 여러 서비스를 나눠 처리 가능하다. `/api/*`는 API 서버 Target Group으로, `/static/*`은 정적 파일 서버로 라우팅할 수 있는 게 예시이다.

**모니터링/로깅** : CloudWatch로 요청 수, 응답시간, 4xx/5xx 에러율 등을 자동 수집한다. Access Log는 S3에 저장해서 장애 발생 시 원인 추적에 사용한다.

# 특징
**매니지드 서비스** : AWS가 로드밸런서 자체의 인프라, 소프트웨어, 패치, 이중화를 다 알아서 처리한다. 사용자는 서버를 직접 세팅하는 게 아니라 설정만 하면 된다.

**다중 계층 지원**  : NLB는 네트워크 계층, ALB는 응용 계층에서 동작한다. 트래픽 종류와 요구사항에 따라 골라 쓸 수 있다.

**동적 확장 대응** : 트래픽 양에 따라 로드밸런서 자체의 처리 용량이 자동으로 늘어나고 줄어든다.     
(이 확장은 즉각적이지 않다. 트래픽이 아주 갑자기 몇 배로 튀면 ELB가 미처 스케일업하지 못해 502/503 에러가 발생할 수 있다. 이런 경우 사전에 AWS Support에 **Pre-warming**을 요청해 로드밸런서 용량을 미리 늘려놔야 한다.)

# 장단점
## 장점
**고가용성 확보** : 여러 AZ에 걸쳐 트래픽을 분산하고 헬스체크로 죽은 대상을 자동으로 제외한다. 서버 한 대가 죽어도 서비스 전체는 계속 살아있다.

**운영 부담과 비용 절감** : 직접 로드밸런서를 구축 및 운영하려면 하드웨어/소프트웨어 세팅, 이중화, 패치 관리까지 다 해야 하는데 ELB는 이걸 다 AWS가 처리한다. 사용한 만큼만 비용을 지불해서 초기 투자 비용도 없다.

**확장성 & 유연한 통합** : Auto Scaling, Route 53, CloudWatch 등 AWS 생태계와 바로 연동된다. 트래픽 급증에도 수동 개입 없이 자동 대응이 가능하다.

## 단점
**AWS 벤더 종속** : ELB는 AWS 전용 서비스라서 다른 클라우드나 온프레미스로 이전할 때 그대로 못 가져간다. 설정 방식이랑 API도 AWS 특화여서 마이그레이션 비용이 크다.

**비용 예측의 어려움 + 추가 과금 구조** : 기본 사용료 외에도 LCU 단위로 트래픽량, 연결 수, 규칙 개수에 따라 추가 과금이 된다. 트래픽 패턴이 불규칙하거나 급증하면 비용이 예상보다 커질 수 있어서 사전 예측이 까다롭다.

**세밀한 커스터마이징의 한계** : Nginx나 HAProxy를 직접 구성하는 것보다 세부 설정 자유도가 낮다. 예를 들어 ALB의 기본 Idle Timeout은 60초인데 이 시간을 넘는 긴 요청이나 WebSocket 연결은 별도로 타임아웃 값을 늘려주지 않으면 중간에 끊긴다.
