# ADR
**ADR(Architecture Decision Record)란?** 아키텍처에 영향을 주는 중요한 결정을 왜 그렇게 했는지와 함께 기록한 짧은 문서이다. 핵심은 “무엇을 했나?” 가 아니라 “왜 그렇게 결정했나?”를 남기는 것이다.

## 왜 필요할까?
코드는 무엇을 커밋은 언제를 보여주지만 **다른 선택지는 뭐였고 왜 버렸는지**는 어디에도 안 남는다. 결정한 사람이 떠나거나 기억이 흐려지면 둘 중 하나가 일어난다.

- 이유를 모르니 못 바꿈 → 의미 없어진 결정을 계속 끌고 감
- 이유를 모르고 바꿈 → 예전에 겪은 문제를 다시 겪음

## Status 종류
- Proposed: 제안됨, 논의 중
- Accepted: 채택됨
- Rejected: 검토했지만 안 하기로 함 (이것도 남긴다)
- Deprecated: 더 이상 유효하지 않음
- Superseded: 새 ADR로 대체됨

## 기본 형식
| 항목 | 내용 |
| --- | --- |
| Title | 번호 + 결정 내용 |
| Status | 현재 상태 |
| Context | 어떤 상황이고 어떤 문제가 있었고 제약 조건은 뭔가 |
| Decision | 그래서 무엇을 하기로 했나 |
| Consequences | 이 결정으로 좋아지는 것, 나빠지는 것, 앞으로 감수할 것 |

# 언제 쓸까?
아래 중 하나라도 해당하면 ADR 후보다.

- **되돌리기 어렵나?** 바꾸려면 데이터 이전이나 대규모 코드 수정이 필요함
- **영향 범위가 넓나?** 여러 서비스나 여러 팀에 걸쳐 있음
- **대안이 실제로 여러 개였나?** 진지하게 비교한 선택지가 2개 이상
- **나중에 "왜?"라는 질문이 나올 것 같나?** 남들이 보면 의아할 만한 선택

## 예시 사례
| ADR 감 | 이유 |
| --- | --- |
| ECS vs EKS | 배포 구조 전체가 달라짐 |
| Terraform state를 어디에 저장할지 | 바꾸려면 state 이전 필요 |
| 모노레포 vs 멀티레포 | 바꾸려면 저장소 구조와 CI 전부 수정 |
| 시크릿 관리 방식 (Secrets Manager, Vault 등) | 모든 서비스가 의존함 |
| 환경 분리 방식 (AWS 계정 분리 vs VPC 분리) | 나중에 쪼개기 매우 어려움 |
| drift 감지 방식 | 운영 정책이고, 대안이 여러 개였음 |

# 결정 내용은 수정하지 않는다
Accepted된 ADR은 내용을 고치지 않는다. 결정이 바뀌면 새 ADR을 쓰고 옛 ADR의 Status만 `Superseded by ADR-0007` 이렇게 바꾼다.

그 이유는 ADR이 애초에 “그 시점에 그 정보로 이렇게 판단했다는 기록” 이기 때문이다. 내용을 덮어쓰면 결정의 역사가 사라진다.
